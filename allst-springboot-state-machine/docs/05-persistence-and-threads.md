# 持久化、并发和多线程带来的变化

## 为什么不把整台机器存进数据库

Spring Statemachine 的实例里有执行器、监听器和当前区域。这些对象不适合当聚合根。本模块持久化的是业务状态：

- 订单：`sm_trade_order.status`，外加支付时间、物流单号。
- 合同：`phase`，以及 `legal_status`、`finance_status`。并行审核时三个字段一起看。
- 发票：`sm_invoice_apply.status`。
- 流水：`sm_transition_log`，三种机器共用，用 `machine_type` 区分。

下次事件用这些字段拼 `DefaultStateMachineContext`，再 `resetStateMachine`。这就是备忘录。合同在 `REVIEWING` 时，备忘录还带两个子上下文，id 分别是 `LEGAL` 和 `FINANCE`，和配置里的 `region` 一致。汇合到待签署之后，阶段不再是 `REVIEWING`，恢复时用扁平上下文。法务和财务的结果字段仍留在表里供查询。

`sendEvent` 返回之后立刻 `stop`。下一笔请求会再创建一台机器。这样机器里的扩展状态不会串到别的订单上。

## 同一张单的事件串行，不同的单并行

`KeyStripedLock` 用业务键做分段锁：`trade:{orderNo}`、`contract:{contractNo}`、`invoice:{invoiceNo}`。

同一键上的两个请求会排队。不同键使用不同的锁对象，支付订单 A 不会挡住订单 B 的发货。

锁在事务之外获取，在事务提交之后释放。如果先开事务再抢锁，两个事务可能都读到旧状态，后提交的那个把先提交的覆盖掉。

这把锁只在一个 JVM 里有效。多实例部署时，同一订单打到两台机器上仍可能并发。表上的唯一流水和订单的 `@Version` 是第二道防线：重复事件号或版本冲突会失败，事务回滚。多实例要再加一把按同一业务键的分布式锁，分段锁的位置可以保持不变。

分段锁的键会留在内存里。示例可以接受。生产环境如果用分布式锁，就不要在进程内无限累积锁对象。

## 状态机实例不能交给别的线程

Spring Statemachine 2.5 的运行实例会把事件放进自己的执行器。本模块每次在请求线程里恢复、发送、停止，不把实例放进业务线程池。

需要异步的是通知，不是机器。`NotifyWarehouseAction` 等动作在转移过程中只登记任务。`AfterCommitExecutor` 看到当前有事务时，把任务挂到 `afterCommit`。提交成功后，任务进入 `stateMachineExecutor`。

这个池的参数：

| 项 | 值 | 作用 |
| --- | --- | --- |
| 核心线程 | 4 | 平时的通知并发 |
| 最大线程 | 8 | 短时高峰 |
| 队列 | 200 | 有界，避免无限堆积 |
| 拒绝策略 | `CallerRunsPolicy` | 队列满时退回调用线程执行，形成反压，任务不会被丢掉 |
| 线程名 | `sm-async-` | 日志里能看出是状态机的后续动作 |

## 多线程之后，具体多了什么

### 1. 请求线程只包住必须原子的那一段

事务里留下状态、库存和流水。通知仓库、通知退款渠道、通知会员在提交之后进行。

收益：

- 支付回调不用等仓库接口返回才给渠道应答。
- 仓库超时不会把已经支付的状态滚回去。
- 通知失败记在异步回执里，可以按订单号重试，重试的是通知，不是再发一次 `ALLOCATE`。

`GET /api/async-tasks` 能看到 `done:warehouse:{orderNo}` 这类回执。这是教学探针。正式审计以 `sm_transition_log` 为准。

### 2. 下单前的两次查询重叠执行

`ParallelPrecheckService` 用 `CompletableFuture` 把 `RiskEvaluator` 和 `StockReader` 提交到同一个池。模拟实现各自睡眠 80 毫秒。两路同时跑时，总耗时接近较慢的那一路，而不是两者相加。

`ParallelPrecheckOverlapTest` 不依赖时钟的绝对值，它断言两段时间区间互相重叠。这样机器忙一点也不会把测试打成偶发失败。

收益：页面在用户点支付之前就能同时看到风险分和库存。预检不是转移条件。真正占库存仍发生在 `ALLOCATE` 的条件更新里，避免用几毫秒前的库存做决定。

### 3. 同一张单不会自己和自己竞争，不同的单仍然并行

两笔订单同时 `ALLOCATE` 最后一件货时，分段锁让它们各自进入自己的事务，库存条件更新保证只有一行更新成功。另一笔进入 `STOCK_SHORT`，库存变成 0。`TradeOrderFlowTest.concurrentAllocateKeepsStockConsistent` 覆盖这条。

收益：吞吐来自“不同订单并行”，正确性来自“同一订单串行 + 库存条件更新”。不需要用一把全局锁把所有履约请求排成一队。

### 4. 超时扫描独占一个调度线程

`PayTimeoutScanner` 按 `statemachine.trade.scan-delay-ms` 周期运行，默认 60 秒。它找出长时间停在待支付、支付中、支付失败的订单，发送 `TIMEOUT`。

收益：不为每张订单保存一个 `Timer`。订单量上去之后，调度线程数量仍然是一个。关单和人工取消走同一条转移，规则不会分叉。

扫描器调用的是外观上的 `fire`，因此每张订单仍有自己的锁和事务。一张关单失败不会把本轮其他订单一起回滚。

## 不要用多线程做的事

- 不要在动作里再开线程去改订单状态。状态只在持有锁的那个事务里回写。
- 不要把 `StateMachine` 实例注入成单例来接收所有订单的事件。工厂按订单号取实例，用完停止。
- 不要用机器自带的 `timerOnce` 做支付超时。实例停止后定时器就没了，重启之后也不会补上。扫描器发事件可以补。

## 提交后通知仍然要能重入

进程可能在事务提交之后、通知执行之前退出。恢复后业务状态已经是待发货，但仓库没收到消息。补偿任务应再次调用通知，而不是再次发送 `ALLOCATE`，否则会再扣一次库存。示例里的动作没有做这层补偿，流水和异步回执用来把这个缺口暴露出来。
