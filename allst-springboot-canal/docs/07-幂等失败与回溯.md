# 07 幂等、失败与回溯

## 消息会重复

两处会产生重复：

1. 消息已经进了 RabbitMQ，进程在 `ack` Canal 之前退出。Canal `rollback` 后再次投递。
2. 消费者写完存储，确认 MQ 之前进程退出。监听容器会再次投递。

主键覆盖写入让重复的 INSERT 和 UPDATE 变成同一次结果。同一 binlog 位点允许再次应用，就是为了让这种重试成功。

## 消息会乱序到达某一个下游

单个队列是单消费者，正常情况下按发布顺序处理。重试和死信重新投递之后，旧消息可能排到新消息后面。`BinlogCursor` 丢掉位点更老的那条。

这个比较依赖 binlog 文件名可以按字符串排序。改过 MySQL `log-bin` 命名、或者文件名没有零填充时，要换比较规则。

同一秒里的多个事件不能用 `executeTime` 排序，MySQL 事件时间经常相同。所以位点用的是文件名加偏移，不是执行时间。

## 下游失败停在哪里

```text
Canal 批次
  发布失败 -> rollback，卡在 Canal，应用日志有“投递失败，回滚后重试”
  发布成功 -> Canal ack
      消费失败 3 次 -> 该下游的死信队列
      另外两个下游不受影响
```

死信队列：

| 队列 | 含义 |
| --- | --- |
| `canal.sync.redis.dlq` | Redis 写入失败 |
| `canal.sync.es.dlq` | Elasticsearch 写入失败 |
| `canal.sync.mongo.dlq` | MongoDB 写入失败 |

应用日志里搜 `同步失败进入死信队列`，能看到主键和 `logfile@offset`。

修复下游之后，在 RabbitMQ 管理台把死信队列里的消息 move 回原来的工作队列（`canal.sync.redis`、`canal.sync.es` 或 `canal.sync.mongo`）。不要 move 回交换机再广播，否则另外两个已经成功的下游会再收一次。再收一次是安全的，但没有必要。

## 对照三个库是否一致

```text
GET http://localhost:1238/api/sync?schema=demo&table=t_product&id=1001
```

看三份 `data` 里的 `_binlogFile` 和 `_binlogOffset`。不一致时，偏移小的那一端还没消费到，或者它的死信队列里有消息。

直接查：

```bash
docker exec -it allst-canal-redis redis-cli HGETALL canal:demo:t_product:1001
curl http://127.0.0.1:9200/demo_t_product/_doc/1001
docker exec -it allst-canal-mongo mongosh canal_sync --eval "db.demo_t_product.find({_id:'1001'}).toArray()"
```

MongoDB 6 的镜像里是 `mongosh`。`_id` 在代码里按字符串主键保存。

## 日志和代码的对应关系

| 日志 | 代码 | 表示 |
| --- | --- | --- |
| 已连接 Canal | `CanalClientRunner.open` | TCP 订阅成功 |
| 已发布到 MQ | `DataChangePublisher` | 这一行已经交给交换机 |
| Canal 批次已确认 | `CanalClientRunner.pull` | 位点往前走了 |
| 已写入 / 已删除 | 三个 `*SyncService` | 下游落库完成 |
| 跳过更旧的变更 | 三个 `*SyncService` | 幂等比较生效 |
| 投递失败，回滚后重试 | `CanalClientRunner.pull` | MQ 没接住，位点没动 |
| 同步失败进入死信队列 | `DeadLetterLogger` | 这一端需要人工处理 |

单元测试覆盖解析和位点比较，不连接真实中间件：

```bash
mvn test
```

`CanalEntryParserTest` 构造 Canal 的 protobuf 行数据，检查 INSERT、DELETE、联合主键，以及事务标记和 DDL 被跳过。`BinlogCursorTest` 检查文件名和偏移的先后。
