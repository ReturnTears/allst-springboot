# 01 目标与架构

## 目标

业务库仍然是 MySQL。商品变更之后，缓存、搜索和文档查询各自要有一份数据，但不能让下单事务自己去写 Redis、Elasticsearch、MongoDB。那样订单接口会绑死三个中间件的可用性。

本模块把这件事拆开：

1. MySQL 照常提交事务，只负责把变更写进 binlog。
2. Canal 伪装成一个从库，把 binlog 解析成行变更。
3. 本应用不直接写三个存储，先发到 RabbitMQ。
4. Redis、Elasticsearch、MongoDB 各自一个队列、一个消费者。

## 为什么不用直连 binlog

`allst-springboot-mysql2es` 使用 `mysql-binlog-connector-java`，客户端自己连 MySQL。Canal 把协议解析、位点记忆、从库伪装留在 Canal Server，应用只消费已经解析好的行数据。官方客户端示例是 [SimpleCanalClientExample](https://github.com/alibaba/canal/blob/canal-1.1.7/example/src/main/java/com/alibaba/otter/canal/example/SimpleCanalClientExample.java)。

Canal Server 也可以直接把消息投到 Kafka、RocketMQ 或 RabbitMQ（`canal.serverMode=mq`）。本项目没有走这条路，而是自己发 RabbitMQ。原因是教学和回溯更直接：解析、投递、消费、落库都在这一个 Spring Boot 工程里，三个下游用同一份 `DataChangeEvent`。

## 运行时组件

| 组件 | 作用 | 代码或配置 |
| --- | --- | --- |
| MySQL 8.0 | 业务库，ROW binlog | `deploy/docker-compose.yml`、`deploy/mysql/init.sql` |
| Canal Server 1.1.7 | 解析 binlog，TCP `11111` | `deploy/canal/instance.properties` |
| 本应用 | 拉取、解析、投递、消费 | `src/main/java/com/allst/springboot` |
| RabbitMQ | 一份变更复制成三份 | `RabbitSyncConfiguration` |
| Redis / ES 7.17 / MongoDB | 三个查询面 | `sync/redis`、`sync/es`、`sync/mongo` |

## 增量，不是全量

Canal 第一次连上时，如果没有指定 binlog 文件和位点，就从 MySQL 当前位点往后读。启动前已经存在的行不会自动进 ES。全量初始化需要另做一次扫表，不在本模块范围内。
