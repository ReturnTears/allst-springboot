# 05 MQ 解耦

Canal 客户端和三个存储之间只通过 `DataChangeEvent` 通信。解析器不引用 Redis、ES、Mongo 的客户端，消费者也不引用 Canal 的 protobuf 对象。

## 拓扑

定义在 `RabbitNames` 和 `RabbitSyncConfiguration`。

```text
canal.sync.exchange     topic，durable
    routing key: canal.change.{schema}.{table}
    binding:     canal.change.#
        canal.sync.redis
        canal.sync.es
        canal.sync.mongo

canal.sync.dlx          direct
    canal.sync.redis.dlq
    canal.sync.es.dlq
    canal.sync.mongo.dlq
```

一条消息发一次，三个队列各有一份。Redis 消费失败不会减少 ES 队列里的那一份。

路由键里的库名、表名会把非字母数字下划线换成 `_`，避免 `.` 被 RabbitMQ 当成单词分隔以外的意外字符。`demo.t_product` 的路由键是 `canal.change.demo.t_product`，能匹配 `canal.change.#`。

某个下游在 `application.yml` 里设为 `enabled: false` 时，对应的 binding 不会创建。交换机上没有绑定的消息会被丢掉，而不是堆在一个没人消费的队列里。

## 序列化

`RabbitTemplate` 和监听容器都使用 `Jackson2JsonMessageConverter`。Boot 默认的 Java 序列化在消费端换成 JSON 时对不上，所以模块里自己声明了 `RabbitTemplate`。

## 顺序和重试

每个监听容器 `prefetch=1`、`concurrentConsumers=1`。同一个队列里按投递顺序处理。三个队列之间并行，不保证 Redis 和 ES 在同一毫秒可见。

消费抛异常时，Spring Retry 最多 3 次，间隔从 1 秒指数增加到 8 秒。用尽之后 `RejectAndDontRequeueRecoverer` 拒绝消息且不重新入队。工作队列配置了死信交换机，消息进入对应的 `*.dlq`。

`DeadLetterLogger` 监听三条死信队列，把 `messageId`、事件类型、主键、binlog 位点打到错误日志。管理台 `http://127.0.0.1:15672` 也能看到这些队列。

## 和 Canal ack 的关系

位点在“发布到 RabbitMQ 成功”后就确认了，不是在三个下游都写完之后。

这样 ES 宕机不会堵住 MySQL 的增量拉取。失败的那一份留在 ES 自己的队列或死信里。代价是：进程在 `ack` 之后、RabbitMQ 落盘之前崩溃，可能丢这一批。演示没有开 publisher confirm。要补这一段，需要确认 broker 已经接住消息再 `connector.ack`。

发布失败则 `rollback`，Canal 会把同一批再次给出。下游因此必须能消化重复消息，见 [07-幂等失败与回溯](07-幂等失败与回溯.md)。
