# 什么时候不要用：反模式与选型

模式是为了让改动变便宜，不是为了显得专业。**先用最朴素的写法，等出现具体症状再引入**——判据是「这段代码现在因为缺少某个结构而难以修改」。

## 一个够用的决策顺序

1. 只有一两个分支、一两个字段？直接写，别抽象。
2. 分支按「类型/渠道」增长 → 策略 + `Map<String, X>` 注入。
3. 分支按「当前状态能否做」增长 → 状态转移表。
4. 一串有序校验 / 过滤 → 责任链（顺序显式指定）。
5. 成功后要挂越来越多无关动作 → 事件；要严格顺序 → 中介者。
6. 步骤相同、细节不同 → 模板方法；只有一步不同 → 回调 / lambda。
7. 第三方接口不兼容 → 适配器；子系统太复杂 → 外观。
8. 想给现有对象加横切能力 → 先看 AOP 有没有现成注解。
9. 遍历大数据量 → 迭代器/游标；同类不变数据重复创建 → 享元或缓存。
10. 引入前问一句：**框架是不是已经做了**（[06](06-spring-patterns.md)）。

## 常见滥用

| 模式 | 常见滥用 | 更合适的做法 |
| --- | --- | --- |
| 单例 | 手写 `static getInstance()`；单例里放当前用户/当前订单 | 用 `@Component`；请求状态走参数、`ThreadLocal` 或原型 bean |
| 工厂方法 | 只有两种实现也建一套 Creator 继承树 | 一个 `switch` 或 `Map` 注入 |
| 抽象工厂 | 产品之间其实可以自由搭配 | 各自独立的策略 |
| 建造者 | 三个字段也写 Builder，且 `build()` 不校验 | 构造器 / 静态工厂；要 Builder 就把约束放进 `build()` |
| 原型 | `Object.clone()` 浅拷贝；把 prototype bean 注入单例 | 深拷贝；`ObjectProvider` 现取 |
| 适配器 | 接口是自己的、能直接改，还多包一层 | 直接改接口 |
| 桥接 | 只有一个维度变化 | 继承或策略 |
| 组合 | 用组合模式去实现复杂规则语义（函数、优先级、时间窗） | SpEL / 规则引擎；组合只表达层级 |
| 装饰器 | 套五六层，排查问题要跳十次调用 | 合并同类横切逻辑，或用 AOP 一处处理 |
| 外观 | 外观里长出完整业务流程、状态分支和补偿 | 拆应用服务 / 引入状态机 |
| 享元 | 把会变的对象放进共享池 | 享元对象必须不可变 |
| 代理 | 同类自调用还指望注解生效 | 拆到另一个 bean |
| 责任链 | 顺序靠 bean 名字母序；链上节点互相读写状态 | `@Order` 显式排序；节点只返回放行/拒绝 |
| 命令 | 失败后不释放幂等键；撤销栈全局单例 | 失败释放；按业务单据隔离历史 |
| 解释器 | 自己写词法/语法解析器，还接受用户输入的 SpEL | 用成熟引擎；限制表达式可访问的类型 |
| 迭代器 | 分页不排序；遍历时允许并发写入不加约束 | 固定排序字段；用快照或 id 游标 |
| 中介者 | 中介者里塞满业务细节，变成新的上帝类 | 它只编排协作，具体动作留在同事类 |
| 备忘录 | 快照是可变引用；历史永久不清理 | 不可变副本；按单据隔离 + 过期策略 |
| 观察者 | 事务内发短信；监听器抛异常回滚主流程；事件成环 | `AFTER_COMMIT`、异步或补偿、约束事件链 |
| 状态 | 用枚举查表硬撑守卫/动作/并发恢复 | 完整状态机（见 `allst-springboot-state-machine`） |
| 策略 | 选择策略的地方又写一个大 `if-else` | 注解标 type，注册时自动收集 |
| 模板方法 | 骨架方法可被覆盖；钩子开七八个 | 骨架加 `final`；变化收敛到两三个抽象方法 |
| 访问者 | 元素类型天天加，每加一次改所有 Visitor | 改用策略或注册表 |

## 最容易出线上事故的五条

1. **事务内发外部消息**：回滚了短信已发出。用 `@TransactionalEventListener(AFTER_COMMIT)` 或事务消息。
2. **AOP 自调用**：`this.method()` 绕过代理，`@Transactional` 静默失效，数据不一致且没有报错。
3. **幂等键失败不释放**：下游抖动一次后，所有重试都被判重复，动作永远不执行。
4. **浅拷贝原型 / 可变享元**：改一个活动把全部活动改坏，且往往是线上才暴露。
5. **责任链顺序错位**：统计排在限流之后、风控排在参数校验之前，规则「看起来配了」但不生效。Sentinel 的 slot 顺序就是典型例子。

## 过度设计的信号

- 为了一个功能新建了 5 个接口、8 个类，但业务分支只有 2 个。
- 阅读一个方法需要在 7 个类之间来回跳，而它做的事一句话能说清。
- 单元测试里大半篇幅在搭 mock 和装配容器，而不是验证业务结果。
- 「以后可能会扩展」是唯一理由，但现在没有任何扩展需求。

出现这些信号，删掉抽象，先把代码写直白；等真的变化来了，再按 [02](02-scenario-map.md) 的症状反查表引入对应的那一个模式。
