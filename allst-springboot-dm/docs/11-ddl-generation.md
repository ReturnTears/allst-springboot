# 11 · 元数据驱动的多方言 DDL 生成

这一篇记录一个完整的新需求：数据库元数据表里存着「表 + 字段 + 方言」，要求按方言生成建表 DDL 并导出 SQL 文件。它是本模块里**模式组合最密集**的一章——不是堆 23 种模式，而是围绕两根变化轴做了一次克制的设计。

## 11.1 需求与本质

元数据表描述目标库的一张表：表名、schema、方言、注释、表选项，以及一组字段（列名、逻辑类型、长度/精度、可空、主键、自增、分区、默认值、ordinal）。要求：

1. 方言**没有固定清单**，还要覆盖 Impala 这种「能建分区」的 OLAP 引擎，以及不常用的库；
2. 类型体系**按方言自定义逻辑类型**；
3. 结果**导出 SQL 文件**，不直接连库执行。

拆开看，这是「两条变化轴 + 一条稳定轴」：

| 轴 | 内容 | 应对手段 |
| --- | --- | --- |
| 变化轴 1：方言 | 类型名、引号、自增、注释语法、分区、表选项 | 策略 + 能力模型 |
| 变化轴 2：规模 | 表/列是动态的 N 条 | Stream 编排 |
| 稳定轴：流程 | 校验 → 分流 → 逐列渲染 → 主键 → 表级子句 → 拼装 | 模板方法 |

架构原则一句话：**稳定流程用模板方法固化，方言差异用策略+能力封装，集合规模用 Stream 编排**。

## 11.2 为什么是「能力模型」而不是「一堆 if-else」

最直觉的写法是每种方言一个 `if (mysql) {...} else if (impala) {...}`，但这次不成立的理由很硬：

- **差异不是「类型名不同」而是「片段有无」**。Impala/Hive 没有主键和自增，却有 `PARTITIONED BY` 和 `STORED AS PARQUET`；ClickHouse 用 `Int64/DateTime` 强类型加 `ENGINE=MergeTree()`；Doris 的主键叫 `UNIQUE KEY`；PG/Oracle 的列注释是**独立的 `COMMENT ON` 语句**，不是内联片段。
- **方言清单开放**。没有固定清单就意味着加方言不能改路由代码。

于是抽象出能力枚举 `Capability`，每个方言只声明自己支持哪些、实现对应钩子：

```
PRIMARY_KEY / AUTO_INCREMENT / INLINE_COLUMN_COMMENT / INLINE_TABLE_COMMENT
POST_DDL_COMMENT / PARTITION / PARTITION_COLUMNS_SEPARATE / TABLE_OPTIONS / IF_NOT_EXISTS
```

模板基类 `AbstractDdlDialect.generate()` 用 `final` 固定流程，按 `supports(Capability)` 决定渲染哪些片段。新增方言 = 新增一个 `@Component` + 一个构造里 `registerType(...)`，模板和路由零改动。

`DialectRouter` 用 Spring 注入的 `List<DdlDialect>` 建 `Map` 索引（策略 + 工厂），**未注册的方言名落到 `GENERIC` 兜底**输出 ANSI 近似 DDL 并给出告警——这正是「没有清单、库可能很偏」的落地答案。

## 11.3 模式与 Stream 编排映射

| 模式 | 对应的类 | 解决的具体问题 |
| --- | --- | --- |
| 策略 Strategy | `DdlDialect` + 10 个实现 | 方言算法各自封装，加方言不改主流程 |
| 能力模型（策略的参数化） | `Capability` | 把「片段有无」变成可查询的声明，替代 if-else |
| 模板方法 Template Method | `AbstractDdlDialect.generate()` | `final` 固定生成骨架，子类只填钩子 |
| 建造者 Builder | `TableMeta.Builder` / `ColumnMeta.Builder` | `build()` 校验表名/方言/重复列名/重复 ordinal，产出可用对象 |
| 外观 Facade | `DdlGenerator`、`GlobalExceptionHandler` | 调用方只给一批元数据，拿回按方言分组的脚本 |
| 工厂方法 / 注册表 | `DialectRouter` | Spring 注入建索引，未注册走兜底 |
| 享元（共享不可变信息） | 各方言构造里的类型登记表 | 类型映射表注册一次、全局复用 |

Stream 的关键发力点（都在 `DdlGenerator` 与模板里）：

- `Collectors.groupingBy(TableMeta::getDialect)` —— 一次分组，每种方言只查一次路由；
- `sorted(comparing(ColumnMeta::getOrdinal))` —— 列顺序稳定，DDL 输出不抖动，版本库 diff 好看；
- `filter(hasText)` —— 可选片段（注释/自增/表选项）为空时自动跳过，不会拼出 `,\n)` 这种语法错误；
- `joining` —— 列、表、文件头全部用收集器拼装，不用 `StringBuilder` 做副作用累积。

这里**故意用顺序流**：DDL 生成是轻量 CPU 活，`parallelStream` 的分组与线程安全开销更大，且 `StringBuilder` 非线程安全。

## 11.4 类型体系：方言自治

元数据里存的是**逻辑类型名**（见 `LogicalTypes`：STRING/INT/BIGINT/DECIMAL/BOOL/DATETIME/...），不是物理类型。每个方言在构造器里用 `registerType("STRING", c -> ...)` 声明自己的映射：同一个 `STRING`，MySQL 是 `varchar(64)`、Oracle 是 `varchar2(64)`、ClickHouse 是 `String`、Impala 是变长 `string`（不写长度）。方言**不认识的逻辑类型直接报 `BizException`**，绝不猜一个物理类型——这是可靠性底线。

`GET /api/dm/ddl/dialects` 返回每种方言的「能力 + 支持类型」矩阵，可以直接看这张自治清单。

## 11.5 10 种方言的 DDL 差异对照

| 方言 | 引号 | 自增 | 主键 | 注释 | 分区/特有语法 |
| --- | --- | --- | --- | --- | --- |
| MYSQL | 反引号 | `AUTO_INCREMENT` | `PRIMARY KEY` | 内联 `COMMENT` | `PARTITION BY HASH` + `ENGINE=...` |
| POSTGRESQL | 双引号 | `BIGSERIAL`/`SERIAL` | `PRIMARY KEY` | 独立 `COMMENT ON` | — |
| ORACLE | 双引号 | `GENERATED BY DEFAULT AS IDENTITY` | `PRIMARY KEY` | 独立 `COMMENT ON` | `TABLESPACE`；无 `IF NOT EXISTS` |
| SQLSERVER | `[]` | `IDENTITY(1,1)` | `PRIMARY KEY` | 扩展属性 `sp_addextendedproperty` | — |
| SQLITE | 双引号 | 绑在主键列 `INTEGER PRIMARY KEY AUTOINCREMENT` | 列级 | — | 弱类型 |
| IMPALA | 反引号 | — | — | 内联 `COMMENT` | `PARTITIONED BY(col type)` + `STORED AS PARQUET`；分区列单独声明 |
| HIVE | 反引号 | — | — | 内联 `COMMENT` | 同 Impala + `IF NOT EXISTS`；`BLOB → binary` |
| CLICKHOUSE | 反引号 | — | — | 内联 `COMMENT` | `Int64/DateTime` 强类型 + `PARTITION BY` + `ENGINE=MergeTree()` |
| DORIS | 反引号 | — | `UNIQUE KEY` | 内联 `COMMENT` | `PARTITION BY` + `DISTRIBUTED BY`（表选项） |
| GENERIC | 双引号 | — | `PRIMARY KEY` | 能力缺失告警 | ANSI 近似写法，兜底 |

一张 Impala 实际输出（来自种子数据的订单事实表）：

```sql
CREATE EXTERNAL TABLE `dwd`.`dwd_order`
(
  `order_id` string,
  `sku` string,
  `amount` decimal(12,2)
)
COMMENT '订单明细事实表'
PARTITIONED BY (`dt` string)
STORED AS PARQUET;
```

注意 `dt` 作为分区列**不在普通列块里**，而是出现在 `PARTITIONED BY`——这就是 `PARTITION_COLUMNS_SEPARATE` 能力驱动的结果。

## 11.6 怎么加一个新方言（如 TiDB / StarRocks）

1. 新建 `XxxDialect extends AbstractDdlDialect`，加 `@Component`；
2. 构造里声明 `EnumSet.of(...Capability...)`，再 `registerType(...)` 注册支持的逻辑类型；
3. 按需覆盖能力钩子：`quote()`、`autoIncrementClause()`、`partitionClause()`、`postDdlStatements()` 等；
4. 加一条 golden DDL 断言测试。`DialectRouter` 自动发现，无需改任何现有类。

如果新方言暂时没实现，元数据里的方言名会落到 `GENERIC` 兜底，不会导致导出失败。

## 11.7 运行与接口

配置：`dm.ddl.output-dir`（默认 `./generated-ddl`，测试用 `target/test-ddl`）。启动后：

```bash
# 1. 灌入 5 张多方言示例元数据
curl -X POST http://localhost:8367/api/dm/ddl/seed

# 2. 看方言能力矩阵
curl http://localhost:8367/api/dm/ddl/dialects

# 3. 预览生成（读库）
curl -X POST http://localhost:8367/api/dm/ddl/generate \
  -H 'Content-Type: application/json' -d '{"dialect":"IMPALA"}'

# 4. 离线生成（请求体直接带元数据，不读库）
curl -X POST http://localhost:8367/api/dm/ddl/generate \
  -H 'Content-Type: application/json' \
  -d '{"dialect":"MYSQL","tables":[{"tableName":"t","dialect":"MYSQL","columns":[{"columnName":"id","logicalType":"BIGINT","primaryKey":true,"autoIncrement":true,"ordinal":0}]}]}'

# 5. 导出 SQL 文件（按方言一个文件）并下载
curl -X POST http://localhost:8367/api/dm/ddl/export \
  -H 'Content-Type: application/json' -d '{"dialect":"IMPALA"}'
curl http://localhost:8367/api/dm/ddl/files
curl -O http://localhost:8367/api/dm/ddl/download/ddl-IMPALA-20261119232600.sql
```

`dialect` 传 `null`/不传时，用元数据自带的方言并按方言分组导出；传具体值时覆盖为同一方言。

## 11.8 工程注意点

- **JPA 懒加载**：`TableMeta.columns` 用 `FetchType.EAGER`，避免离线生成时 session 外访问抛 `LazyInitializationException`；`ColumnMeta.table` 加 `@JsonIgnore` 防止双向关联反序列化递归。
- **路径安全**：`DdlExportService.resolve()` 拒绝 `../` 和子目录，下载接口只能拿到输出目录下的文件。
- **DDL 不是 DML**：这里只导出文件、不连库执行；若将来要直接执行，需把 `IF NOT EXISTS` / `DROP` 前缀纳入能力，并注意多数数据库 DDL 是隐式提交。
- **元数据来自可信来源**：虽然做了标识符引号，但表名/列名/默认值最终进 DDL，若来源可被外部写入，仍应加标识符白名单校验。

验证：`mvn -o -pl allst-springboot-dm test`，59 个测试全绿（其中 DDL 相关 26 个）。
