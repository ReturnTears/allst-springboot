# 生命周期

分两层：Spring 容器何时拉起和关掉各套服务器，以及一条 TCP 连接自己的状态怎么变。

## 容器

三套自建 Netty 都实现 `SmartLifecycle`，`isAutoStartup()` 用接口默认值 true。phase 越小越先启动，停止时顺序相反。

| Bean | phase | 启动时做什么 | 停止时做什么 |
| --- | --- | --- | --- |
| `NettyTcpServerLifecycle` | 0 | 创建 boss、worker、业务线程组并 bind | 关服务器 Channel，再依次 `shutdownGracefully`（最多等 5 秒） |
| `NettyWebSocketServerLifecycle` | 0 | bind 看板端口 | 同上，没有业务线程组 |
| `DeviceSimulator` | 100 | 创建客户端线程组，枪开始拨号 | 先停枪（`running=false` 后再关连接，避免重连），再关线程组 |
| WebFlux 的 `WebServerStartStopLifecycle` | 2147481599 | 启动 Reactor Netty | 先于上面三套停止 |

2147481599 是 Spring Boot 3.4.5 里 `org.springframework.boot.web.reactive.context.WebServerStartStopLifecycle.getPhase()` 的返回值。升级 Boot 后如果启动顺序变了，用 javap 再对一下这个方法。

因此正常启动顺序是：设备端口、看板端口、模拟枪开始拨号、最后才是 HTTP。HTTP 能访问时，TCP 端口已经在监听。拨号本身是异步的，`LOGIN` 日志可能比 `Netty started` 略晚一行。同为 phase 0 的设备和看板互不依赖，谁先 bind 都行。

`ApplicationRunner`（`GatewayStartupLogger`）在全部 `SmartLifecycle.start()` 之后执行，所以打印出来的是实际端口，端口写 0 时也能打出系统分配的值。

`server.shutdown=graceful` 和 `spring.lifecycle.timeout-per-shutdown-phase=20s` 给每个 phase 的停止留出时间。三组线程各等最多 5 秒，串行下来仍落在 20 秒里。

`start()` 只有 bind 成功才把 `running` 设为 true。bind 失败时把已经创建的线程组关掉再把异常抛出去，避免端口没听上、线程却残留。

## 一条设备连接

```text
accept
  -> channelRegistered
  -> channelActive
  -> Pipeline 装好，开始读
  -> LOGIN / HEARTBEAT / SCAN / ACK / LOGOUT
  -> 读空闲或异常或对端关闭
  -> channelInactive（按 Channel 身份决定要不要推 OFFLINE）
  -> channelUnregistered
```

重连进来的是一条新 Channel。旧 Channel 的 `channelInactive` 仍会发生，但登记表里已经换成新连接时，不会把新会话删掉。

## 一条看板连接

```text
accept
  -> HTTP 握手
  -> HandshakeComplete
  -> 登记 Channel，下发 SNAPSHOT
  -> 之后只收服务端推来的文本帧
  -> channelInactive 时移出广播列表
```

## 一台模拟枪

```text
start
  -> connect
  -> 成功则 LOGIN，并在该 EventLoop 上排心跳
  -> 失败或之后断开
  -> 若 running 仍为 true，延迟重连
  -> stop 把 running 设为 false，关闭后不再拨号
```

集成测试把 `netty.client.simulator-enabled=false`，这条自动拨号不会跑。测试自己 new 一个 `WarehouseDeviceClient`，用完调用 `stop()`。
