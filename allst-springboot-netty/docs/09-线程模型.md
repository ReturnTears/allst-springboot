# 线程模型

目标与 Turms 文档里写的同一件事：线程数量由配置和 CPU 决定，不随在线枪的数量增加。每条连接只是某个 EventLoop 上的一段状态。

## 名字

`application.yml` 把日志前缀写成了 `%thread`。一次完整链路里能看到这些名字（数字后缀会变）：

| 线程 | 谁在上面跑 |
| --- | --- |
| `warehouse-boss-*` | 只 `accept`。默认 1 条。多条 acceptor 不会让一台机器接受得更快 |
| `warehouse-worker-*` | 读字节、切帧、解析 JSON、把写操作真正发到网卡。`worker-threads: 0` 时用 Netty 默认值，即 CPU 核数的两倍 |
| `warehouse-biz-*` | `WarehouseServerHandler`。`business-threads: 0` 时取 `max(2, CPU 核数)` |
| `dashboard-boss-*` / `dashboard-worker-*` | 看板的接受和握手、文本帧写出 |
| `device-client-*` | 全部模拟枪的拨号、心跳、收指令、回 ACK |
| `scanner-sim` | 一条守护线程，只负责定时挑枪发模拟扫码 |
| `reactor-http-nio-*` | WebFlux 的 HTTP 和 SSE |

`WarehouseGatewayTest` 跑通时，登录和扫码的日志在 `warehouse-biz-*`，枪收到指令的日志在客户端 EventLoop，看板握手的日志在 `dashboard-worker-*`。这三组名字同时出现，说明业务处理没有回到 accept 线程，看板也没有占用设备的 worker。

## 一次下发跨了哪些线程

1. HTTP 请求在 `reactor-http-nio-*` 上进入 `DeviceConsoleController`。
2. 控制器只做查找和 `writeAndFlush`，不在这根线程上等待设备回 ACK。
3. Netty 把编码和写出排到该 Channel 注册的 `warehouse-worker-*`。
4. 枪在 `device-client-*` 上读到 `COMMAND` 并写出 `ACK`。
5. 服务端 worker 解码后，把消息投递到 `warehouse-biz-*`，在那里改指令状态并广播。
6. 广播对每条看板连接调用 `writeAndFlush`，实际发送发生在 `dashboard-worker-*`。

`Channel` 的 `writeAndFlush` 可以从别的线程调用，这是 Netty 的约定。不要从别的线程直接改 Pipeline 里非线程安全的解码器状态。

## 不要做的事

- 不要在 `warehouse-worker-*` 上查数据库或调用阻塞 HTTP。解码器后面的 Handler 已经换到 `warehouse-biz-*`；业务线程同样不该被阻塞，数据库客户端应使用异步驱动，或者再丢到有界的业务池。
- 不要为每台枪 `new` 一个 `EventLoopGroup`。模拟器已经演示了多连接共享一组的写法。
- 不要把看板上的广播循环写回设备的 worker。现在的广播在业务线程上发起，真正的 socket 写落在看板自己的 EventLoop。
- 心跳使用所在 Channel 的 `eventLoop().scheduleAtFixedRate`，不为每台枪再开一条 `Thread`。

## 和 HTTP 那组 Netty 的边界

Reactor Netty 的 EventLoop 由 `NettyReactiveWebServerFactory` 创建。本项目没有把它注入到 `ServerBootstrap.group(...)`。合用一组线程可以少占一些线程，但一个慢的 HTTP 控制器就会推迟扫码帧的读取。仓储接入里设备通道比看板查询更在意延迟，所以分开。

若以后要合用，应在自动配置里显式拿出 Reactor Netty 的 `LoopResources` 再传给设备服务，并保证业务 Handler 仍然不在这组线程上执行阻塞调用。当前代码没有走这条捷径。
