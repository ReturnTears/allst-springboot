# 业务场景

## 仓里实际在发生什么

手持扫码枪和巷道终端不适合用一次一连的 HTTP：

- 枪要一直在线，WMS 才能主动告诉它「去 A-03」
- 仓库 Wi-Fi 会闪断，断了要自己重连，重连后要重新登记
- 半开的 TCP 连接看起来还在，应用层必须靠心跳发现「人已经走了」
- 仓管要在看板上立刻看见扫码流水，而不是刷新页面

这和即时通讯的接入层是同一类问题。编写时（2026-10-25）对照过三个公开项目：

| 项目 | 当时页面上的 star | 和本项目的关系 |
| --- | --- | --- |
| [crossoverJie/cim](https://github.com/crossoverJie/cim) | 约 9.5k | Spring Boot + Netty 的 IM。`cim-server` 管长连接，`cim-client` 是终端，`cim-route` 管登录和转发。本项目把这三块收成一个进程里的 TCP 服务、TCP 客户端和 WebFlux |
| [turms-im/turms](https://github.com/turms-im/turms) | 约 1.9k | 面向十万到千万连接的 IM 引擎。网关用 Netty 做非阻塞 I/O，线程数不随在线人数涨。本项目的 boss / worker / 业务线程分离是同一原则的缩小版 |
| [YeautyYE/netty-websocket-spring-boot-starter](https://github.com/YeautyYE/netty-websocket-spring-boot-starter) | 约 1.9k | 用注解把 Netty WebSocket 嵌进 Spring Boot。本项目不套这层注解，Pipeline 和握手事件留在代码里，方便看生命周期 |

没有把这三个仓库的代码拷进来。借用的是结构：长连接接入、自定义帧、心跳、会话表、服务端主动推送。

## 本项目里的角色

| 真实系统里的角色 | 在这里是谁 |
| --- | --- |
| 扫码枪固件 | `WarehouseDeviceClient`，默认由 `DeviceSimulator` 拉起 3 台 |
| 设备接入网关 | `NettyTcpServerLifecycle`，端口 9000 |
| WMS 下发指令 | `POST /api/devices/{deviceId}/commands` |
| 仓管看板 | `index.html` + WebSocket 9001 |

内存里的会话表和最近 500 条扫码足够把这条链路跑通。生产里会话通常还要进 Redis，离线指令进数据库或消息队列。那些存储可以换，Netty 这条接入链路不用换。

## 这条 TCP 通道不要拿来传文件

帧长默认 64KB，含 7 字节帧头。扫码、心跳、短指令够用。照片和固件包应走 WebFlux 的 HTTP 上传，不要把大文件塞进长连接，否则一个慢连接会把写缓冲区打满，后面的指令也发不出去。写缓冲区高水位时，下发接口返回 429。
